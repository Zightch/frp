## 2. 服务端本机网卡/IP 快照层已落地

截至 2026-04-21，当前轮第 2 个子步骤已经完成最小代码落地：`frps` 启动时会先抓取本机全部网卡及 IPv4/IPv6 地址，并在后台持续轮询维护一份当前可用地址快照；Windows / Linux 的收口入口已经按平台拆开，但这一轮还没有把该快照接入 `effective_ip` 绑定、管理 API 或 WebUI。

本次已完成的实现收束如下：

- 新建 `frps/internal/system/`，新增 `NetworkSnapshotService`，负责启动时首轮采集、后台定时轮询、线程安全快照读取和关闭收口。
- 新增 `Snapshot` / `NetworkInterface` / `IPAddress` 结构，当前快照同时保留“按网卡分组的 IP 列表”和“去重后的当前可用 IP 集合”，IPv4 / IPv6 都会进入集合；特殊值 `0.0.0.0`、`::` 仍保留给后续 `effective_ip` 绑定规则处理，不混入物理地址快照。
- 新增 `network_collect_windows.go`、`network_collect_linux.go` 和 `network_collect_other.go`，按 build tag 区分平台收口；当前 Windows / Linux 都统一走 `net.Interfaces()` 地址发现主路径，但平台分流点已经固定，后续如需补平台特化逻辑可直接在各自文件扩展。

- 当前这一步只新增“地址发现与轮询”基础层，还没有修改数据库 schema、`GroupRuntime`、listener 绑定地址、异常态派生或 WebUI 表单。

本次固定下来的边界如下：

- 本机地址快照属于服务端运行时基础设施，由 `frps` 启动时自动拉起，后续步骤统一复用这份快照，不再各处重复自行枚举本机地址。

- 快照内容包含所有已发现网卡，以及每张网卡上的全部 IPv4 / IPv6 地址；同一地址在网卡维度内会去重，在全局可用地址集合内也会去重。
- 当前实现还不负责提供管理 API，也不负责判定“分组异常”；这些都留给后续步骤基于同一份快照继续接入。

## 8. 在线 frpc 会话已支持随管理侧配置变更刷新

截至 2026-04-21，本轮针对代码巡检发现的第 1 个明显缺陷已经完成修复：管理 API 修改分组或隧道配置后，`frps` 现在会定位该分组的在线 `frpc` 会话并立即触发刷新，不再只能等客户端手工断开后才生效。

本次已完成的实现收束如下：

- `frps/internal/control/` 新增按 `group_id` 重载运行态的能力：控制面现在会登记在线分组会话，支持按分组 ID 重新读取 `GroupRuntime` 并向在线客户端重新下发 `config.push`。
- 刷新过程会同步重置该分组当前的公网 listener / UDP 会话；对正常配置变更走热刷新，对 token 被重置或前一版配置仍未 ack 的场景，主动断开控制连接，交给 `frpc` 现有自动重连逻辑重新登录。
- `frps/internal/control/repository.go` 补充了按分组 ID 读取运行态的方法，避免刷新路径只能依赖 token 查询。
- `frps/internal/api/management.go` 已把刷新动作接入分组更新、分组删除、token 重置、隧道创建、隧道更新、隧道删除；其中隧道跨分组移动会同时刷新旧分组和新分组。
- `frps/internal/app/app.go` 已把 control server 注入管理 API，收口为后端内部联动，不引入新的 HTTP 接口。
