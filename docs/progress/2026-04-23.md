## 1. `RefreshGroup()` / 轮询扫描并发窗口已补齐并修正重复 pending 误关会话缺陷

截至 2026-04-23，当前轮“端口冲突检查 / 热更新交互”的“竞争窗口补齐”第 1 个子步骤已经完成：已把 `RefreshGroup()` 与 `scanNonListeningTunnelRuntimeIssues()` 并发下的重复 `config.push` / 陈旧快照回退窗口落成正式测试，并顺手修掉了一处真实实现缺陷。

本次已完成的实现与测试如下：

- `frps/internal/control/runtime_recovery_scenario_test.go`
  - 新增 `TestServerScenarioDeduplicatesMatchingRefreshAndScanRecoveryPush`
    - 直接把 active session 固定在“空配置保活”状态；
    - 让轮询扫描先命中恢复路径并在 `control.config_push.before_write` 卡住；
    - 再并发触发 `RefreshGroup()`，验证不会重复下发第二个 `config.push`，也不会因为“已有 pending config”误关当前 session。
  - 新增 `TestServerScenarioIgnoresStaleScanSnapshotAfterRefreshAdvancesVersion`
    - 让轮询扫描先抓到旧快照 `v2`，再由 `RefreshGroup()` 推进到新快照 `v3`；
    - 验证旧扫描结果后续不会再补推 `v2`，不会把已生效的 `v3` listener / snapshot 回退成旧版本。
- `frps/internal/control/session.go`
  - 新增 `refreshPendingConfig()`：
    - 当已有 pending config 且其“已下发目标快照”与本次刷新目标一致时，不再把它视为冲突；
    - 同时会把最新 `GroupRuntime` 元数据覆写到 pending 上，保证后续 ack 生效时使用的是最新分组元信息。
- `frps/internal/control/refresh.go`
  - `RefreshGroup()` 现在会先计算“本次真正想推进的目标快照”（完整快照或空配置快照），再决定如何处理已有 pending config。
  - 命中“同一目标快照已在飞行中”时，改为去重返回，不再关闭 session。
  - 只有 pending config 与当前刷新目标确实不同，才继续沿用原来的保守策略关闭 session。
  - 新增 `samePushedConfigSnapshot()`，用 `config_version + generated_at + tunnel 集合` 精确判断“是否同一份已下发配置”，避免把新版本误并到旧版本上。

本次收束后的边界如下：

- 当前只修复“同一目标快照并发到来时的重复 pending 误关会话”；不同目标快照并发时，仍保持保守关闭策略，后续由剩余竞争窗口步骤继续覆盖。
- 当前已正式覆盖两类关键窗口：
  - 同目标恢复去重：不双推、不误断会话
  - 旧扫描结果晚到：不把已推进的新快照回退成旧快照

## 2. 空配置保活后的断线重连恢复路径已补齐，确认旧 listener / runtime issue / pending 不泄漏到新 session

截至 2026-04-23，当前轮“端口冲突检查 / 热更新交互”的“恢复路径与故障补齐”第 1 个子步骤已经完成：已把“空配置保活后的客户端断线重连”补成正式回归，覆盖旧 session 退出后新 session 接管时的 listener、runtime issue 和 pending config 清理边界。

本次新增测试如下：

- `frps/internal/control/effective_ip_scenario_test.go`
  - 新增 `TestServerScenarioReconnectAfterEmptyConfigClearsOldRuntimeIssueAndListeners`
    - 先让旧 session 因 `effective_ip` 不在本机而缩成空配置保活；
    - 再在本机地址恢复后断开旧 session，并由新 session 重新登录；
    - 验证旧 listener 已全部清空，旧 runtime issue 不会遗留到新 session，最终只保留新 session 的单份 listener 和 group slot。
  - 新增 `TestServerScenarioReconnectAfterPendingRecoveryPushDropsOldPendingConfig`
    - 让旧 session 先进入空配置态，再由轮询扫描触发“完整配置恢复 push”，故意停在未 ack 的 pending full-config 状态；
    - 随后断开旧 session 并让新 session 重新登录；
    - 验证旧 pending config 不会阻塞或污染新 session，新 session 能重新完成初始下发、ack 和 listener 恢复。

本次收束后的边界如下：

- 旧 session 已处于 `empty_config` 或 `pending_full_config` 时，只要连接结束，后续新 session 登录不会继承旧 pending 状态。
- 旧 session 退出后，group slot 会被正确释放并重新分配给新 session；不会出现“无 active session 但 slot 仍占用”的残留。
- 新 session 在健康快照下完成首次 `config.ack` 后，会重新建立 listener 并清掉旧 runtime issue；当前这条恢复路径下未发现新的实现缺陷。
