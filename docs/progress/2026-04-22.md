# 2026-04-22

## 1. 端口冲突判定矩阵与共享冲突模型已收口

截至 2026-04-22，当前轮“`frps` 端口冲突检测最小闭环”的第 1 个子步骤已经完成：端口冲突检测的共享判定模型、比较矩阵、触发入口和预计代码落点已经收口，后续实现统一按同一套监听占位语义推进。

本次已完成的规则收束如下：

- 端口冲突检测的核心对象不是原始 `tunnel` 文本，而是“会声明一个公网 listener 占位”的监听声明；后续管理面和控制面都按同一模型比较，不各写一套规则。
- 监听声明的最小比较维度已经固定为：`protocol`、`effective_ip`、`remote_start`、`remote_end`，以及用于报错定位的 `group_id` / `tunnel_id`；`single` 只是 `remote_start == remote_end` 的特例，`range` 不再展开成逐端口数组后再比较。
- 管理面口径已经固定为“配置占位”而不是“当前在线会话占位”：只要分组和隧道都处于启用态，就视为该声明会占用对应公网监听空间，不要求 `frpc` 已在线。
- 因此，禁用分组或禁用隧道当前不参与占位；但凡 `group.enabled`、`group.effective_ip`、`tunnel.enabled`、`tunnel.protocol`、`tunnel.remote_start`、`tunnel.remote_end` 发生变化，都必须重新校验受影响的监听声明集合。
- 协议维度已经收口为完全隔离：`tcp` 只与 `tcp` 比较，`udp` 只与 `udp` 比较，二者不共享同一冲突空间。
- 端口区间比较规则已经固定：
  `single-single` 看端口是否相同；
  `single-range` 看单点是否落入区间；
  `range-range` 看两个区间是否相交。
- IP 比较规则已经固定为“按监听空间是否重叠”：
  具体 IPv4 只与相同 IPv4 冲突；
  具体 IPv6 只与相同 IPv6 冲突；
  `0.0.0.0` 与全部 IPv4 具体地址冲突；
  `::` 与全部 IPv6 具体地址冲突。
- `0.0.0.0` 与 `::` 之间额外固定为冲突关系：虽然它们在配置语义上分属 IPv4 / IPv6 wildcard，但当前 Go/Windows 环境下两者会落到同一类 wildcard socket 资源，第二次绑定会直接失败；为了避免管理面放过、控制面再报底层 bind 错误，本轮统一按冲突处理。
- 具体 IPv4 与具体 IPv6、具体 IPv4 与 `::`、具体 IPv6 与 `0.0.0.0` 当前不按静态冲突处理；这部分继续按地址族语义隔离，不因为当前平台可能出现 dual-stack 行为就扩大到全部跨族冲突。
- 为保持配置行为可预期，`0.0.0.0` 与具体 IPv4、`::` 与具体 IPv6 当前仍按冲突处理；即使某些平台/调用顺序下底层 socket 允许 wildcard 与 specific 同端口并存，管理面也不接受这类重叠配置。
- 共享 helper 的预计落点已经固定为新的 `frps/internal/ports` 包：管理面负责把数据库里的分组/隧道投影成监听声明，控制面负责把 `GroupRuntime` / `ConfigSnapshot` 投影成监听声明，底层冲突比较函数本身不依赖 `api` 或 `control` 包。
- 共享 helper 的输出形态已经收口为“返回冲突双方及原因”，而不是只返 `bool`；后续管理面需要把它转成稳定的 API 错误文案，控制面则需要把它转成结构化日志和运行态 bind 失败语义。
- 管理面第一批必须接入的入口已经确认：`createTunnel()`、`updateTunnel()`、`updateProxyGroup()`；其中 `updateTunnel()` 必须忽略自身旧记录，`updateProxyGroup()` 在 `effective_ip` 或 `enabled` 变化时必须按整组隧道重算。
- 控制面第一批必须接入的入口已经确认：`ensureTunnelListeners()` 和 `effective_ip` 本地重绑路径；即使管理面静态校验已经兜住，控制面仍要把“外部进程占用端口”或“极端竞态下的运行态冲突”收敛成明确的端口冲突错误，而不是直接透传底层 `listen` 文案。

本次固定下来的边界如下：

- 当前轮只处理 `frps` 公网 listener 端口冲突，不处理 `frpc` 本地目标端口冲突。
- 当前轮优先保证“配置层冲突”与“运行态 bind 冲突”的口径一致，不在第一步引入前端侧预测逻辑或额外的持久化字段。
- 当前轮不把“操作系统是否偶然允许 overlap bind”当作配置合法性的标准；配置层一律按监听空间语义和已确认的 wildcard 特判来收口。
- 当前轮仍然不会让“分组是否在线”影响管理面冲突判定；否则同一份配置在离线时可写、上线时失败，行为不可预测。

本次执行的验证如下：

- 本地 Go 绑定实验：对 `tcp` / `udp` 分别验证 `0.0.0.0`、`[::]`、`127.0.0.1`、`[::1]` 的同端口绑定关系，确认当前 Go/Windows 环境下 `0.0.0.0` 与 `[::]` 互相冲突，而 wildcard 与 specific 在部分场景下可共存。
