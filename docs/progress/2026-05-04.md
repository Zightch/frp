## TCP work pool 容量与补货窗口收口

- 当前已将 `frps` 默认 `tcp work pool` 容量从 `8` 固定提升到 `64`。
- `frps` 在公网 TCP 新连接到达且当前没有 idle `work conn` 时，不再立刻打掉连接，而是执行一次短时等待：
  - 等待上限收口为 `200ms`
  - 期间如果 `frpc` 预补的新 `tcp work connection` 注册完成，会立即唤醒等待方
- `frpc` 现有预补逻辑保持不变，但与新的服务端等待语义配合后，形成当前最小闭环：
  - 忙掉一条 `work conn`
  - 立即触发补池
  - 新连接如果正好撞上补货窗口，`frps` 会短等并接住，而不是直接失败
- `frps/internal/control/wiring/work_connection_test.go` 已新增覆盖：

## go target 高压短连接问题定位

- 当前已把 `frps` 默认 `tcp work pool` 容量继续固定扩大到 `1024`。
- 放大后重新回放：
  - `python test/e2e_tcp_perf.py --target-mode go --output-dir test/tmp/perf-pool1024-go`
  - 结果：`stability_attempts=40977 success=981 failures=39996`
- 结论：
  - 扩大 pool 只能略微缓解，但不能解决 `go target` 这类问题。
  - 当前失败主因不是 pool 容量，而是 `tcp work` 建连握手与“入池可分配”之间存在竞态。
- 已通过 debug 复现直接确认：
  - `frpc` 日志首错：`tcp work pool failed error=expected tcp.work.ready, got stream.open`
  - 随后 `runSession` 被该错误打断，控制会话关闭，`frpc` 进入重连
  - `frps` 随即看到：
    - `tcp work stream open failed`
    - `frpc control session ended error=EOF`
- 宏观逻辑问题：
  - `frps` 在处理 `tcp.work.register` 时，先把新 work conn 注册进 session pool，再回写 `tcp.work.ready`
  - 一旦公网短连接高压进入，别的 goroutine 可以在 `ready` 还没发完、甚至 `frpc` 还没读到 `ready` 之前，就先从 pool 里拿走这条连接并下发 `stream.open`
  - `frpc` 这时仍处在 `openTCPWorkConn()` 的握手阶段，按协议它还在等待 `tcp.work.ready`
  - 结果收到的第一帧变成了 `stream.open`，于是直接报错 `expected tcp.work.ready, got stream.open`
  - `workPoolLoop` 当前把任何补池错误都视为致命错误，于是整个 control session 被连带打掉
  - control session 一掉，公网监听随之消失，压测侧就集中表现成大量 `ConnectionRefused`
- 当前收口：
  - `ConnectionRefused` 只是后果
  - `tcp work stream open failed` 也只是后果
  - 真正的起点是：`tcp.work.register -> tcp.work.ready -> 入池可分配` 这段顺序不正确

## go target 高压短连接最终收口

- 当前已完成两处核心修复：
